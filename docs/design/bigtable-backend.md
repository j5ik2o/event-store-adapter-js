# Design of the Bigtable Storage

This document is the design record of the Bigtable storage in `event-store-adapter-js`. Check the [README](../../packages/library/README.md) and the [schema document](../../packages/library/docs/BIGTABLE_DATABASE_SCHEMA.md) for current usage.

- Normative sources: the hub (j5ik2o/event-store-adapter) `docs/spec/core-contract.md` and `docs/spec/storage/bigtable.md` (v5), and the hash specification and ADRs they cite. This document adds no rules and changes no specification. Rule numbers (BT-7, W-8, etc.) are the numbers in those sources.
- Conformance data: `conformance/` (v1.3.0). The 42 common scenarios, the 12 Bigtable scenarios and the 1 shared scenario are all run against the Bigtable storage, and so are the value tables (4 FNV-1a 64 references and 10 envelope cases) (`packages/library/src/internal/test/conformance/conformance-bigtable.test.ts`). The only exclusions are the 8 cases that `Date` (millisecond precision) cannot represent: the 4 `core-time-*` scenarios in `scenarios/core/write-read.json` and the 4 `occurred-at-*` cases in `values/occurred-at.json`; 87 required cases pass, with no failed, unverified or not-representable case. The report is written to `coverage/conformance/bigtable.json`.
- Paths below are relative to `packages/library/src/`. "Test" means a jest test in that file. The tests marked "emulator" run against the Cloud Bigtable emulator started by Testcontainers (a pinned `google-cloud-cli` image); nothing connects to the real service and no real credentials are used.

## 1. Decisions

| Decision | Choice | Reason |
|:--|:--|:--|
| SDK | `@google-cloud/bigtable` `^7.5.0`, an optional peer dependency, used only through `Bigtable#request` | The rules fix the request shapes (column range filters, latest cell, timestamp 0, conditional updates), the assembly of split rows and the resumption. The high-level `Table`/`Row` API hides all of them. `request` also gives one place where every data and admin request is observed. |
| Entry point | `event-store-adapter-js/bigtable`, separate from the main entry | The main entry must not load the Bigtable SDK (the same approach as Spanner and SQLite). The entry itself uses only the client the caller passes, so it needs no runtime import of the SDK. |
| Client ownership | The caller creates and closes the `Bigtable` client | The library never creates tables, families or clients. |
| Initialization | `BigtableEventStore.initialize` and `create` are separate (BT-D1); `initialize` checks the column families first | `create` never creates or completes a table or a row. |
| Commit point | One `CheckAndMutateRow` on the head row; sent once, never retried | A lost response is an unknown outcome (BT-7); a retry would see the committed head and fail as an optimistic lock conflict. |
| Authentication | An optional `accessToken` function, called once before every data and admin request | Under an emulator the SDK attaches no credentials, so a token path that is never called would pass silently. The token is not cached and never appears in an error message. |
| Journal write failure | `onJournalWriteFailure` and `BigtableJournalWriteFailure` (kind `journal-write-failure`) | The conformance data observes this notification; widening `RetentionFailure` would break a shared type contract. |
| Retention type | The existing `SnapshotRetention`; TTL is a `configuration-error` | Same type as the memory and SQLite storages (BT-D4, BT-13). |
| Contract rule | `ContractRule` gains `"BT-16"` | The envelope limit violation reports that rule (BT-16, BT-D6b). |
| Exclusions | Change feed (BT-14, BT-15, BT-17 beyond the configuration error) is not provided in the first version (BT-D8). A migration tool is not provided because earlier versions had no Bigtable storage. | |

## 2. Rule-to-test mapping

| Rule | Behavior | Test |
|:--|:--|:--|
| BT-1 | Every request carries the client's app profile (`""` when none) and the full table name | `internal/bigtable-requests.test.ts`: "app profile and table name" |
| BT-2 | The column families are checked on `create` and `initialize`: missing families, a missing table, no rule, an age-based rule and a two-version rule are a `configuration-error` | `internal/bigtable-store-configuration.test.ts`: "verifyBigtableStore"; `internal/bigtable-event-store.test.ts` (emulator): "create and initialize" |
| BT-3 | Row key `H ‖ L16 ‖ A`; ids with colliding hashes never see each other, and the config row `0x00` is outside every range | `internal/bigtable-row-keys.test.ts`; `internal/bigtable-event-store.test.ts` (emulator): "hash collisions" |
| BT-4 | Journal keys end with an 8-byte big-endian number; the byte order is the numeric order; ranges use fixed-width numbers | `internal/bigtable-row-keys.test.ts` |
| BT-5, BT-12 | A journal row is created only when `event:envelope` is absent; an existing row is verified, never overwritten; a late writer cannot revive a retired history | `internal/bigtable-stored-rows.test.ts`: "writeJournalRow"; `internal/bigtable-event-store.test.ts` (emulator): "a stale writer that writes a retired history row later cannot revive the history" |
| BT-6 | Cells are written at timestamp 0, a replaced column is deleted in full first, and conditions look at the latest cell only | `internal/bigtable-event-store.test.ts` (emulator): "cell layout and versions" |
| BT-7, H-1 | Order: validate and serialize, read the head, check W-3/W-8, write the previous event, conditional head update, write the new tail. A conditional update that does not succeed is an optimistic lock conflict. A lost response is a storage error and is not sent again | `internal/bigtable-faults.test.ts` (emulator): "failures before and at the commit point"; conformance `bigtable-previous-event-write-failure`, `bigtable-new-tail-write-failure`, `bigtable-cas-response-lost` |
| BT-8, BT-9 | The latest snapshot comes from one head read; events use the first head read's `h` for the whole call; a gap in the journal range is a storage error | `internal/bigtable-read-operations.test.ts`; `internal/bigtable-event-store.test.ts` (emulator): "append and read" |
| BT-10 | Split values, repeated row keys and `ResetRow` are assembled; an interrupted stream resumes after the last completed row; no progress or an unfinished row is a storage error | `internal/bigtable-row-collector.test.ts`; `internal/bigtable-read-rows.test.ts`; `internal/bigtable-requests.test.ts`: "range reads" |
| BT-11, BT-12, BT-13 | Retention reads only the history state of rows `1..h`, retires the active histories older than the newest `n`, keeps the event cells, and a failure is reported without changing the append | `internal/bigtable-event-store.test.ts` (emulator): "snapshot retention"; `internal/bigtable-stored-rows.test.ts`: "retainBigtableHistory"; `internal/bigtable-faults.test.ts` (emulator): "notifications never change a committed append" |
| BT-13, S-4 | Notification targets (logger, `onRetentionFailure`, `onJournalWriteFailure`) that throw or reject never change a committed append; the tests assert that the paths were called and that the stored data exists | `internal/bigtable-faults.test.ts` (emulator); `internal/bigtable-journal-write-failure-notification.test.ts` |
| BT-16, BT-D6b | An envelope above the limit is a `contract-violation` with rule `BT-16` before any write; the limit is recorded in both tables and mismatches are a `configuration-error`; the range is 17 to 8388608 | `internal/bigtable-event-store.test.ts` (emulator): "envelope limit (BT-16)", "input rejected before anything is written"; `internal/bigtable-event-store-input-validation.test.ts`; conformance `bigtable-envelope-over-limit`, `bigtable-envelope-limit-*`, `bigtable-seeded-*` |
| BT-17 | A `changeFeed` setting is a `configuration-error` before any request | `internal/bigtable-event-store-input-validation.test.ts`; conformance `bigtable-change-feed-unsupported` |
| BT-D1 | `create` never initializes; `initialize` refuses tables that already hold a configuration row; the configuration JSON has unique top-level keys and a strict `keep_snapshot_count` | `internal/bigtable-configuration.test.ts`; `internal/bigtable-store-configuration.test.ts`; `internal/bigtable-event-store.test.ts` (emulator): "create and initialize" |
| BT-D6a | The envelope is the fixed binary format; the 10 reference cases match; trailing bytes, a wrong length and an unknown version are a storage error | `internal/bigtable-envelope.test.ts`; conformance `bigtable-envelope-*` |
| Authentication | Every data and admin request calls the token source once and carries `authorization: Bearer`; a failing or non-ASCII token sends nothing | `internal/bigtable-access-token.test.ts` (emulator); `internal/bigtable-requests.test.ts` |
| Format compatibility | Rows written in the Rust shape are read by this storage; rows written by this storage have the Rust keys, cell names and envelope bytes | `internal/bigtable-rust-layout.test.ts` (emulator) |
| Entry point | `./bigtable` export, optional peer dependency, isolation from the other entries, packed package type-check and execution | `bigtable.test.ts`, `bigtable-package.test.ts`, `bigtable-entry-isolation.test.ts`, `packages/tests/e2e/bigtable-entry-isolation.test.cjs`, `packages/tests/e2e/external-consumption.test.cjs`, `packages/tests/e2e/workspace-consumption.test.cjs` |
| Documents | The README examples (first run and reopen) are identical in English and Japanese, type-check against the public types and run against the emulator | `internal/bigtable-documents.test.ts` (emulator) |
| Request splitting | Not applicable beyond ReadRows resumption: every other request touches one row | BT-10 tests above |

## 3. Conformance run

`pnpm --filter event-store-adapter-js run coverage --runInBand` writes `bigtable.json` next to the memory, DynamoDB, SQLite and Spanner reports in `coverage/conformance` (or `CONFORMANCE_REPORT_DIR`). `conformance-bigtable.test.ts` fails when a required case is not run, failed, unverified or not representable. The harness creates a new pair of tables per case in one emulator, injects faults through the test hooks (a `replace-request` fault before the request is sent, a `replace-response` fault after the conditional update was sent), and reads the stored history through the same public request path. The result recorded in the last local run: passed 87, failed 0, unverified 0, not-representable 0, not-applicable 8 (the nanosecond cases and their shared siblings that `Date` cannot represent), 74 cases that target other storages are reported as `backendNotApplicable`.
