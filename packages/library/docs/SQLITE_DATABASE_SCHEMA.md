# SQLite storage schema

## Layout

This document describes the file that `SqliteEventStore.initialize(...)` creates and `SqliteEventStore.create(...)` opens, through the `event-store-adapter-js/sqlite` entry point. See [the current README](../README.md) for usage. The layout is the same as the Rust version's, so either implementation can read and write a file created by the other.

One local database file holds five tables. All of them are `STRICT`, so the database itself rejects values that cannot be converted to the declared type. `aid` is `TEXT COLLATE BINARY` in every table that has it, and the primary key index must use the `BINARY` collation too. A file whose column or primary key index uses `NOCASE` or `RTRIM` is rejected when opened, because it would read `User-A` and `User-a` as one aggregate. There is no `head_transition` table, because this version provides no change feed.

| Table | Primary key | Other columns |
|:--|:--|:--|
| `journal` | `(aid, seq_nr)` | `occurred_at_ns INTEGER`, `manifest TEXT`, `payload BLOB` |
| `head` | `aid` | `type_name TEXT`, `seq_nr INTEGER`, `event_occurred_at_ns INTEGER`, `event_manifest TEXT`, `event_payload BLOB` |
| `snapshot_current` | `aid` | `seq_nr INTEGER`, `manifest TEXT`, `payload BLOB` |
| `snapshot_history` | `(aid, seq_nr)` | `manifest TEXT`, `payload BLOB` |
| `config` | `singleton` | `store_id TEXT`, `layout_version INTEGER`, `keep_snapshot_count INTEGER`, `retention_mode TEXT`, `change_feed_enabled INTEGER` |

`seq_nr` is an `INTEGER NOT NULL` with `CHECK (seq_nr BETWEEN 1 AND 9007199254740991)`. `aid` is `<typeName>-<value>` and is always compared for exact equality, never with `LIKE`.

## Configuration

The `config` table holds exactly one row (`singleton = 1`):

| Column | Value |
|:--|:--|
| `store_id` | a lower-case UUID, generated by `initialize` |
| `layout_version` | `1` |
| `keep_snapshot_count` | the client's `retention.count`, or `NULL` without retention |
| `retention_mode` | `delete` |
| `change_feed_enabled` | `0` |

`create` compares the row with the client's settings in one read transaction. A different retention count, layout version, retention mode, a `change_feed_enabled` of `1`, a malformed `store_id`, or a missing row is a `configuration-error`. `create` never completes a missing definition.

Each connection checks that the bundled SQLite is 3.51.3 or later (compared part by part as integers) and sets and reads back `busy_timeout` (`lockWaitMilliseconds`, default 5000), `locking_mode = normal`, `journal_mode = wal`, `synchronous = 2` (FULL) and `read_uncommitted = 0`.

## Initialization

`SqliteEventStore.initialize({ path, retention? })` initializes an empty file in one `BEGIN IMMEDIATE` transaction: it creates the five tables and the `config` row. A file that already holds any table, index, view or trigger is a `configuration-error` and nothing is created. `create` never initializes a file, and a missing file is a `storage-error` that does not create it. A TTL retention or `changeFeed` setting is a `configuration-error` before the file is opened.

```typescript
import { SqliteEventStore } from "event-store-adapter-js/sqlite";

const input = { path: "/var/lib/app/events.sqlite3", retention: { count: 3 } };
const initialized = await SqliteEventStore.initialize(input);
const opened = await SqliteEventStore.create(input);
```

## Records

- `journal` holds every event. `head` holds the latest event's number, time, manifest and payload, and `type_name`.
- `snapshot_current` holds the latest snapshot. `snapshot_history` holds older snapshots only when `keep_snapshot_count` is set.
- Integers are bound and read as `BigInt` and have the `integer` storage class. `manifest` is `text` and `payload` is a `blob`.
- `occurred_at_ns` is the millisecond time multiplied by 1,000,000. Reading it rounds toward negative infinity to milliseconds (-1 ns is -1 ms).

## Writes and reads

An append checks and serializes first, then runs on the store's one connection without yielding: `BEGIN IMMEDIATE`, read the head, compare, write `journal`, `head`, `snapshot_current` and `snapshot_history`, then `COMMIT`. Any failure before `COMMIT` is rolled back and nothing is visible.

- A number not above the head, including a duplicated primary key, is an `optimistic-lock-conflict` carrying the head number. A gap is a `contract-violation` (W-8), and a snapshot number different from the event's is W-9.
- Waiting for another connection's write lock longer than `lockWaitMilliseconds` is a `storage-error`, never an optimistic lock conflict. A failure of `COMMIT` is a `storage-error`, and the library does not renumber.
- Reading the latest snapshot reads `head` and `snapshot_current` in one read transaction. Reading events reads `head` and then `journal` up to the head in one read transaction. A commit by another connection in the middle is not mixed in. A missing number below the head is a `storage-error`.

## Retention

When a store has `retention: { count }`, an append with a snapshot writes the snapshot to `snapshot_history`. Right after `COMMIT`, a separate `BEGIN IMMEDIATE` transaction keeps only the newest `count` snapshots of that aggregate (including the one just written) and deletes the older ones. It never deletes `snapshot_current`, `head` or `journal`.

A failure of this cleanup is rolled back and reported through the logger and `onRetentionFailure`. The append stays successful even if those notification paths throw or reject, and the next append with a snapshot cleans up again. TTL retention is not provided and is a `configuration-error`.

## Operations

- Close the store with `close()` before the process exits. `close()` is safe to call repeatedly, and operations after it are a `storage-error`.
- Several stores and several processes on the same host can open one file. Appends are serialized by SQLite's write lock and checked by sequence number.
- Do not put the file on a network file system, and do not open it through `file:` URIs, shared caches or `ATTACH`: the library resolves `path` to an absolute file name and opens it by itself.
- To change the retention count, stop every client and change `keep_snapshot_count` with an external procedure; a client with a different count is refused.
