# Bigtable storage schema

## Layout

This document describes the two tables that `BigtableEventStore.initialize(...)` prepares and `BigtableEventStore.create(...)` opens, through the `event-store-adapter-js/bigtable` entry point. See [the current README](../README.md) for usage. The layout is the same as the Rust version's, so either implementation can read and write tables created by the other.

You create the two tables and their column families yourself, in an instance that already exists. The library never creates a table or a column family.

| Table | Column families | Row key |
|:--|:--|:--|
| journal | `event`, `history`, `config` | `P ‖ U64BE(seq_nr)` |
| head | `head`, `snapshot`, `config` | `P` |

`P = H ‖ L16 ‖ A`, where `A` is the UTF-8 bytes of the aggregate ID (`<typeName>-<value>`), `L16` is the byte length of `A` as an unsigned big-endian 16-bit number, and `H` is the FNV-1a 64 hash of `A` as 8 big-endian bytes. The length makes `P` of one aggregate never a prefix of another's, even when the hashes collide. A row key is compared as bytes, and `seq_nr` is 8 big-endian bytes, so the byte order of the journal rows is the numeric order of `seq_nr`. The configuration row of each table has the one-byte row key `0x00`, which no data row key can equal.

Every data column family (`event`, `history`, `head`, `snapshot`) keeps exactly one version (a garbage collection rule of "at most 1 version") and has no age-based rule. A table whose family is missing, or whose rule is anything else, is rejected when opened. `config` is only checked for existence. Every cell is written with the timestamp 0 and a replaced column is first deleted in full, so a column holds one cell.

## Configuration

Each table holds one row with the key `0x00`, and its cell `config:metadata` is a JSON object with the same value in both tables:

| Key | Value |
|:--|:--|
| `store_id` | a lower-case UUID, generated by `initialize` |
| `layout_version` | `1` |
| `keep_snapshot_count` | the client's `retention.count` as a decimal string such as `"2"`, or `null` without retention |
| `retention_mode` | `"delete"` |
| `envelope_limit_bytes` | the client's `envelopeLimitBytes`, `1048576` by default |

The top-level keys must be unique, and a `keep_snapshot_count` with a leading zero, an exponent or a number type is rejected. When `create` opens the tables, the two rows must be equal and must match the client's `retention.count` and `envelopeLimitBytes`; any difference is a `configuration-error`. There is no change feed in this version, so passing `changeFeed` is a `configuration-error`.

## Initialization

1. Create the journal table with the column families `event`, `history` and `config`, and the head table with `head`, `snapshot` and `config`. Give the four data families a rule of at most one version.
2. Call `BigtableEventStore.initialize(input)` once. It checks the column families, then writes the configuration cell to both tables with a conditional update that only succeeds when the cell is absent. If either table already has a configuration row, nothing is written and the call is a `configuration-error`.
3. Open the tables with `BigtableEventStore.create(input)` with the same settings. `create` never initializes anything: missing tables, missing families or missing configuration rows are a `configuration-error`.

The `Bigtable` client is created and closed by the caller. Against an emulator, set `BIGTABLE_EMULATOR_HOST` or pass `apiEndpoint`; either makes the SDK use an unencrypted connection without credentials.

## Records

| Table | Cell | Value |
|:--|:--|:--|
| journal | `event:envelope` | the event envelope |
| journal | `event:has_snapshot` | `1` if a snapshot was written with the event, otherwise `0` |
| journal | `history:state` | `active` or `retired` (only with retention) |
| journal | `history:envelope` | the snapshot envelope kept as history (only while `active`) |
| head | `head:seq_nr` | the head sequence number as 20 ASCII digits |
| head | `head:last_event` | the event envelope of the head |
| head | `head:has_snapshot` | `1` or `0` |
| head | `snapshot:current` | the latest snapshot envelope |

All numbers are big-endian. An event envelope is `0x01 ‖ U16(aid length) ‖ aid ‖ U64(seq_nr) ‖ I64(occurred_at_ns) ‖ U32(manifest length) ‖ manifest ‖ U32(payload length) ‖ payload`; a snapshot envelope is `0x01 ‖ U64(seq_nr) ‖ U32(manifest length) ‖ manifest ‖ U32(payload length) ‖ payload`. Trailing bytes, a wrong length or an unknown version byte make the envelope unreadable, which is a `storage-error`. A single envelope is at most `envelopeLimitBytes` bytes; a larger one is a `contract-violation` with rule `BT-16` before anything is written.

## Writes and reads

An append runs in this order. Input is validated and serialized first, then the head row is read with strong consistency and the new `seq_nr` is compared with its head `h`. The event of `h`, which only the head row holds so far, is written to its journal row, unless that row already exists. Then one conditional update of the head row moves it forward; it succeeds only when `head:seq_nr` is still `h` (or still absent for the first event), and its success is the commit point. Finally the new tail event is written to its journal row.

- A conditional update that does not succeed is an `optimistic-lock-conflict`. If its response is lost, the append is a `storage-error` and the request is not sent again; a retry sees the committed head and gets an `optimistic-lock-conflict`.
- Failing to write the previous event stops the append before the head moves. Failing to write the new tail row after the commit does not change the result: it is reported to `onJournalWriteFailure` and the logger, and the next append writes the missing row.
- A journal row is created only when it has no `event:envelope`. A late writer therefore never overwrites an existing row, and never revives a `retired` history.

Reads fetch the head row once and use that `h` for the whole call. `getLatestSnapshotById` reads `head:*` and `snapshot:current` from that one row. `getEventsByIdSinceSeqNr(id, start)` returns nothing if there is no head or `start > h`, only the head event if `start = h`, and otherwise the journal rows in `[start, h)` followed by the head event. A gap in the journal range is a `storage-error`. A range read that is cut off resumes after the last completed row.

## Retention

Without `retention`, no history is kept and the journal rows hold only events. With `retention: { count }`, an append that carries a snapshot also writes the snapshot as `history:envelope` in the journal row with `history:state = active`. After the commit, the library reads only the `history:state` cells of the rows `[1, h]`, keeps the newest `count` active histories, and sets older ones to `retired` while deleting their `history:envelope`. The `event` cells are kept, so a `retired` row can still be read as an event and cannot be recreated by a late writer. A failure of this step is reported to `onRetentionFailure` and the logger, never changes the successful append, and is retried by the next append with a snapshot. TTL retention is not supported (`configuration-error`).

## Operations

- Use one application profile for the live operations (`appProfileId` of the `Bigtable` client), so that reads and the conditional updates meet in one cluster.
- `accessToken` is called before every request, data and admin alike, and is not cached. Do not log it; the library never puts it into an error message.
- A notification target that throws does not change the result of a committed append.
- The tests run against the Cloud Bigtable emulator through Testcontainers and never connect to the real service.
